# 哈士喵素材档案 · 元宝全量

元宝 App 里「眼镜猫 → 哈士喵」这个项目，**所有能抢救出来的图片产出**。

**314 个文件 / 180.6 MB**。含 304 张从元宝本地缓存恢复的图 + 10 个桌面散件。

打开 [`index.html`](index.html) 看图廊（缩略图在本页，点开是原图）。

---

## 为什么要抢救

这个项目在元宝里谈了几十轮，**很多图看着有，但一次都没点过下载**。元宝没有「导出全部图片」的入口，对话一多，这些图就只剩客户端缓存这一份残骸。

而缓存会被清理、会被新内容挤掉、会在重装客户端时归零。

所以做了这次抢救：把 App 缓存里的图片按字节全量提出来，去重、分组、编号、建清单。

## 恢复了什么、没恢复什么

**恢复了**：图片本体，逐字节原样，带 sha1。

**没恢复**：对话正文。这一条要说清楚，不是没试：

- 元宝是 WebView2 套壳，数据在 `%LOCALAPPDATA%\com.tencent.yuanbao\EBWebView`
- `Local Storage` / `Session Storage` / `IndexedDB` 里搜「哈士喵 / 眼镜猫 / 八向 / 白模 / 绿幕 / status-candidate」，**命中 0**
- 缓存里命中关键词的 48 个条目，解开 gzip 后逐个看，都是项目自己的 HTML 文档（如 8 向导演台），**不是聊天记录**
- 原因：对话是流式响应，不落磁盘缓存；正文只在服务端

**要做全量正文，只能从元宝界面里手动导出/分享**，本地做不到。

## 怎么恢复的

```
EBWebView\Default\Cache\Cache_Data     638 个条目
   ↓  读前 16 字节判 magic（PNG/JPG/GIF/WEBP）
526 张图片
   ↓  sha1 去重（缓存里同一张图会存多份）
304 张唯一图
   ↓  按尺寸 + 绿占比分组
4 组 + 编号
```

绿占比的算法：缩到 64×64，统计 `G > R+30 且 G > B+30` 的像素比例。> 0.35 判为绿幕类 —— 这个阈值能把绿幕拼板和普通成图干净分开。

重建命令：`python _build/build.py`（输入是 `_yb_stage/`，那是从缓存直接提取的原始文件，未入库）。

## 清单字段

`清单/图片清单.csv`（UTF-8 BOM，Excel 直接开）与 `清单/图片清单.json`：

| 字段 | 说明 |
|---|---|
| `组` | 所属分组 |
| `文件` | 归档后的文件名，`序号_原缓存ID.扩展名` |
| `原缓存ID` | 元宝缓存里的文件名，如 `f_000378`，便于回溯 |
| `宽` `高` `模式` | 像素尺寸与色彩模式 |
| `字节` | 文件大小 |
| `绿占比` | 0~1，>0.35 即绿幕类 |
| `sha1` | 内容指纹，跨仓库查重靠它 |
| `完整性` | `完整` / `截断(缺N字节)` / `非图片` |
| `来源` | `元宝 App 缓存` / `桌面` |

## 已知问题

- **7 张缓存记录尾部被截断**，缺 13~54 字节。画面完整，Pillow 加 `LOAD_TRUNCATED_IMAGES` 可正常读；清单里标了 `截断`。
- **222 张重复图被丢弃**（同一张图在缓存里存了多份，sha1 相同），没有入库，也没有另存。
- **文件名不含语义**。缓存里没有原始提示词，所以只能按尺寸/绿占比分组、按序编号，做不到「这是猫耳」这种命名。语义靠 `总览/` 的大图人工认。
- 图上有「元宝 AI生成」水印的，是元宝自己加的，没有去除。

## 和另一个仓库的关系

- 本仓库：**原始产出归档**，只做抢救和记录，不改图
- [`hashimiao-paperdoll`](https://github.com/604665656/hashimiao-paperdoll)：**编辑器与工程化素材**，那里放的是经过裁切、去背、归一化之后的可用资产，以及那套三件套工具

原始稿会烂在缓存里，工程稿会随代码演进被覆盖 —— 两个都留着，才叫记录。
